# CC-LLM 古汉语强化：数据、训练与评测方案

采用“高质量、可追溯的多任务混合 SFT”。根据 v1 实测，v2 先建立约 5.3 万条核心训练集，可选审核任务最多再加入 8K，并独立构建三任务各 600 条 Dev。标点按实际监督 token 预算控制，不再机械追求原来的 8 万条。 不建议直接将三份数据按来源比例混合，更不建议为了凑齐 Fùxì 的 21 类任务，生成大量未经验证的答案。

这套方案的核心目标是：让已经完成 Phase1、Phase2 的 CC-LLM 获得古汉语任务能力，同时能够解释提升来自哪些数据、哪些任务，以及 PGCA 是否真正有贡献。

## 一、官方资料核验：三份数据实际上提供了什么

| 数据集 | 官方确认的规模 | 可靠的监督内容 | 主要限制 |
| ------ | ------------ | ------------- | ------- |
| [Chinese Classical Corpus](https://huggingface.co/datasets/gujilab/chinese-classical-corpus?utm_source=chatgpt.com) | 12,005 条篇章级原文；1,924,378 条双向翻译指令；46,546 条标点指令 | 古今翻译、断句标点、典籍元数据、字书内容 | 指令数据主要集中在翻译与标点；与 HistoryTrans 存在共同上游   |
| [HistoryTrans](https://huggingface.co/datasets/HistoryTrans/Dataset?utm_source=chatgpt.com) | 765,294 条，官方提供 train/validation/test | 古文到现代汉语的翻译对 | 主要来源同为 Classical-Modern；不能直接与上一数据集简单相加 |
| [EvaHan 2024](https://circse.github.io/LT4HALA/2024/EvaHan.html?utm_source=chatgpt.com) | 约 1,000 万汉字训练语料；约 5 万汉字测试语料 | 专家校订的古汉语断句与标点 | 训练数据须注册获取；不是可直接通过 HF 下载的通用指令数据 |

## 二、具体数据配比：v2 核心目标 53,000 条

这里建议把“可靠核心任务”和“有条件扩展任务”分开，而不是按三份来源的原始数据量采样。

以下数量和比例是实验起点，不是论文已经验证的最优配比；实际入选数量必须在质量审核、去重、去污染后确定。

| 训练任务 | 初始目标条数 | 预期数据来源 |
| ------- | ------- | ---------- |
| 古文 → 现代汉语 | 38,000 | Gujilab + 最多 13K 新增 HistoryTrans |
| 现代汉语 → 古文 | 10,000 | Gujilab |
| 古文断句及标点 | 5,000 | Gujilab；监督 token 占比目标 30%–40% |
| 字书知识：字头、部首、古代释义摘录 | ≤4,000 | Gujilab《说文解字》|
| 可靠典籍元数据与出处识别 | ≤4,000 | Gujilab `corpus` |

前 53,000 条是核心初始目标；如 5K 标点的监督 token 占比仍低于 30%，可补采到最多 6K，仍不达标就报告失败。最后两类合计最多 8,000 条，质量不达标时减少总量，不补充伪标签。v1 标点仅占样本 33.3%，却占监督 token 71.9%；按本轮均长，5K 标点预计约占 34.8%，实际仍由编码报告验收。

### 两个实际采样原则

HistoryTrans 的作用是补充，不是必须采满 13K。 如果跨来源去重后，新增合格译文不足 13K，可以从 Gujilab 中补充尚未使用的可靠平行对，或者降低翻译总量。

本轮不使用 EvaHan，标点全部来自 Gujilab，实验明确记为“不含 EvaHan”。后续取得授权数据后另开对照版本，不把自动来源的标点质量与专家校订数据等同。

这比按固定来源比例分配更稳健。

### 数据抽样不能只看样本数

最终还要生成一张实际混合报告，包含每种任务的：

- 合格候选数、采样数、独立篇章数。
- 来源分布、时代分布、简繁分布。
- 平均、P95 和 P99 的实际 Char Tokenizer 长度。
- Assistant 参与 loss 的 token 数及占比。

原因是：一条翻译样本可能有数百个输出 token，而一条作者问答可能只有几个 token。即使两类样本各占 5%，它们对训练梯度的贡献也不相等。

## 三、数据处理：按这个顺序实施

在 CC-LLM 下使用数据版本标签 `ancient_sft_v2`；统一以 `data/downstream/ancient/raw` 存放原始数据，`benchmark` 存放评测数据，`train/prepared` 和 `train/final` 存放候选及最终产物。不自动覆盖既有版本。处理过程为：

原始数据下载与版本固定

HF revision、Git commit、文件 SHA256、许可证记录

统一 Schema 与数据质量过滤

字段映射、字符完整性、翻译对齐、标点对齐

跨来源去重与 Benchmark 去污染

同源译文、简繁变体、同篇章片段、测试集重合

按作品／篇章分组划分 Train / Dev

先分组，再生成任务变体和采样混合

生成 ms-swift messages JSONL

编码验收、长度分布、配比报告、训练 Manifest

### 1. 原始数据下载与解析

Gujilab 和 HistoryTrans 分别位于 `data/downstream/ancient/raw/chinese-classical-corpus` 与 `data/downstream/ancient/raw/HistoryTrans`，本地和服务器保持相同相对布局。

HistoryTrans 只使用官方 `train` 分区，取 `inputs` 作为古文，`truth` 作为译文。`results` 和 `BLEU` 是数据中存在的额外字段，不应将 `results` 误当成标准译文，也不能把其中 BLEU 直接视作人工质量标注。

HistoryTrans 的 `validation`、`test` 应单独保留；为了避免与 Gujilab 的共同上游重叠，还需要将这些分区中的古文从其他来源的训练候选中排除。

### 2. 质量过滤

| 数据类型 | 推荐验收规则 |
| ------ | ----------- |
| 古今平行翻译 | 原文、译文均非空；排除明显错位、截断、乱码、译文与原文相同等异常 |
| 标点数据   | 移除标点后的输出与输入逐字对齐；不能凭模型猜测修复缺字 |
| 古籍元数据  | 标明作品、篇章、作者等来源；只使用可核验字段 |
| 《说文解字》 | 过滤未解决的 `□`、缺字、错字；古代原释不能自动当作现代释义 |
| 所有任务   | 保留简繁原貌；排除 Unicode 损坏、异常控制字符及不可信生成答案 |

长度阈值不要过早固定。可以从古文 8–256 字、标点片段 30–240 字开始筛查，然后根据质量与实际 tokenizer 长度分布调整。

优先使用 NFC 规范化；简繁转换可用于辅助判重，但不要直接把所有繁体古文改为简体训练。你希望检验 CC-LLM 对汉字音形与长尾汉字的处理能力，保留一定的繁体、异体字分布很有价值。

### 3. 去重和去污染

这是整个方案中最重要的数据工程步骤。

需要同时维护三个标识：

```
source_id      原始数据源
document_group 原始作品、卷、章或可追溯篇章
pair_group     古文与现代译文组成的唯一平行对
```

先将简繁、标点、空白差异规范化用于比较，再执行精确去重和近重复检测。

具体要求是：同一古文的不同译文、反向翻译、同篇章断句片段不能跨分区泄漏。优先通过 corpus 精确包含定位真实卷/章，必要时使用可靠来源篇章标签，无法确定才退回整书或隔离。跨书重复不再传递合并整部作品；选定 Dev 组后，从 Train 排除同篇章、共享平行对/近重复组、完整包含或共享 24 字片段的记录。HistoryTrans 来源有歧义或无法恢复时隔离。

Dev 每项核心任务 600 条，每项至少 5 部书、10 个独立组，单书不超过 20%；不再使用对少数大组做 2% 哈希抽样的方式。输出分任务 Dev，训练端分别评估三个任务 loss，并可按预先固定的宏平均 loss 选 checkpoint。测试集不能用于调整分组或采样。

对于 C³Bench，应利用其测试原文建立去污染索引，对所有任务使用统一的原始古文指纹。对 Fùxì，要检查测试输入和答案型样本是否存在直接或近似复制。短的名句、书名和成语容易产生正常重合，需要保留“精确重合”和“可能重合”两类统计，并在人工确认后隔离高风险记录，而不是简单删除所有包含相同汉字短语的文献。

需要特别说明：之前的 Phase2 已经进行了古籍数据继续预训练。现在做 SFT 去污染，无法消除 Phase2 可能发生的预训练重合。 如果发现 CPT 与测试文本有实质重合，应在实验报告中单独披露，不能将 SFT 数据干净等同于整个模型完全未见过相关测试材料。

### 4. 统一 SFT 输出格式

使用做 CSC 时熟悉的 `messages` 格式。

```

{
  "messages": [
    {
      "role": "user",
      "content": "将下列古文翻译成现代汉语，只输出译文：\n子曰：学而时习之，不亦说乎？"
    },
    {
      "role": "assistant",
      "content": "孔子说：学了知识后经常复习它，不也是很愉快吗？"
    }
  ]
}

```

这里只是格式示例，实际 `assistant` 内容必须来自通过审核的监督数据，不能由示例模板随意生成。

训练文件只需标准 `messages`。来源、任务类别、篇章 ID、质量评分、哈希等信息建议放在一份同 ID 的 `metadata.jsonl` 中，供采样和审计使用，不必全部注入 prompt。

对标点任务，输出必须保持原始字符不增删，仅插入规定的标点符号；对分类与出处任务，输出也应该尽量短且格式一致。

## 四、实现约定

- 实现入口为 `python -m scripts.data_factory.ancient_sft.run inspect|prepare|repartition|finalize`，配置与操作说明见 `scripts/data_factory/ancient_sft/`。
- 原始输入根目录为 `data/downstream/ancient/raw`，默认输出根目录为 `data/downstream/ancient/train`，Benchmark 路径不变；不含 EvaHan，5K 标点初始配额由 Gujilab 提供。
- 使用现有 Char tokenizer，ms-swift 的 `qwen3 + enable_thinking=false`，长度 2048；直接调用实际框架 labels 统计 assistant loss token，不用裸答案长度代替。
- Train 核心 53K，可选知识任务另计；Dev 按任务独立留出 1,800 条。知识/出处样本及疑似污染记录未审核不入选。HistoryTrans 官方 validation/test 必须提供作为跨来源排除集。
- 篇章优先，整书回退，不随机拆句、不跨书传递合并。已校验的 v1 eligible 候选可通过 repartition 复用；不改写旧产物，不恢复隔离或此前已删数据。
- 正式训练就绪需同时满足核心 Train 配额、Dev 数量/作品/篇章/集中度和标点监督 token 占比，不能只检查两个集合非空。
- 训练入口为 `scripts/train/finetune/ancient.sh`；它从 final metadata 构建不改写源文件的 channel 运行视图，记录 `c2m/m2c/punctuate` 三项 Dev loss，以等权宏平均 `eval_macro_task_loss` 选择 checkpoint。
- 来源不足、严格过滤和作品上限导致的缺额如实报告；诊断模式不能导出正式训练文件。文件版本/许可证未知时明确标记，不推断已验证。
